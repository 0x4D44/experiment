# Flux - Puzzle Game Architecture Design
**Date:** 2025.11.06
**Game Concept:** Mathematical toggle puzzle based on modular arithmetic

## Game Overview

### Core Mechanic
- Grid of cells, each with state 0-3
- Clicking a cell increments it and all neighbors by 1 (mod 4)
- Goal: Get all cells to state 0 (or specified target state)
- Operations commute (order doesn't matter)
- Based on linear algebra over Z/4Z

### Visual Design
- Terminal-based with ANSI colors
- States: 0=█ (black), 1=█ (blue), 2=█ (green), 3=█ (yellow)
- Cursor for cell selection
- Move counter
- Win detection with visual feedback

### Core Types

### Linear Solver (Solvability Check)

#### Mathematical Foundation
- Each cell state is in Z/4Z
- Clicking cell i affects cells {i} ∪ neighbors(i)
- System: Ax ≡ b (mod 4), where:
  - A[i][j] = 1 if clicking j affects i, else 0
  - x[j] = number of times to click cell j
  - b[i] = amount needed to reach target from initial state

#### Implementation
```rust
/// Matrix over Z/4Z
pub struct Mod4Matrix {
    rows: usize,
    cols: usize,
    data: Vec<u8>,  // Values in 0-3
}

impl Mod4Matrix {
    pub fn new(rows: usize, cols: usize) -> Self;
    pub fn get(&self, row: usize, col: usize) -> u8;
    pub fn set(&mut self, row: usize, col: usize, value: u8);
    pub fn gaussian_elimination(&mut self) -> Option<Vec<u8>>;
}

/// Check if puzzle is solvable
pub fn is_solvable(grid: &Grid, target: &[CellState]) -> bool;

/// Find a solution (if exists)
pub fn solve(grid: &Grid, target: &[CellState]) -> Option<Vec<usize>>;
```

### Puzzle Generator

#### Strategy
1. Start with solved state (all zeros)
2. Apply random clicks
3. Record initial state
4. Verify solvability with solver
5. Filter for interesting puzzles (not too easy/hard)

## Game Loop

```rust
fn main() -> Result<()> {
    let mut renderer = Renderer::new();
    let levels = LevelPack::main_campaign();
    let mut state = GameState::new(levels.get_level(0).unwrap());

    loop {
        renderer.render(&state);

        match InputHandler::read_command() {
            Some(Command::Click) => {
                state.click_at_cursor();
                if state.is_won() {
                    renderer.show_win_screen();
                    // Advance to next level
                }
            }
            Some(Command::Move(dir)) => state.move_cursor(dir),
            Some(Command::Reset) => state.reset(),
            Some(Command::Quit) => break,
            _ => {}
        }
    }

    Ok(())
}
```

## Testing Strategy

### Unit Tests
1. **Cell State**: Increment operations, modular arithmetic
2. **Grid Operations**: Click mechanics, neighbor calculations
3. **Topology**: Neighbor relationships for different topologies
4. **Linear Solver**: Gaussian elimination over Z/4Z, solution verification
5. **Puzzle Generator**: Generated puzzles are solvable

### Integration Tests
1. **Complete Game Flow**: Start to win condition
2. **Level Progression**: Moving between levels
3. **UI Rendering**: Visual output correctness (snapshot testing)
4. **Solvability**: All generated puzzles are solvable

### Property-Based Tests
1. **Commutativity**: Click order doesn't matter
2. **Invertibility**: 4 clicks = identity
3. **Solvability**: Solved puzzles verify correctly

## Difficulty Progression

### Tutorial (Levels 1-3)
- 2x2 and 3x3 grids
- Simple patterns
- 1-3 optimal moves
- Introduction to mechanics

### Easy (Levels 4-6)
- 3x3 and 4x4 grids
- Rectangular topology
- 3-6 optimal moves
- Learn commutativity

### Medium (Levels 7-10)
- 4x4 and 5x5 grids
- Some with diagonal neighbors
- 6-10 optimal moves
- Pattern recognition

### Hard (Levels 11-15)
- 5x5 and 6x6 grids
- Custom topologies
- 10+ optimal moves
- Complex strategy required

## Open Questions
1. Should we implement undo? (Adds complexity but improves UX)
2. Show optimal move count to player? (Could be frustrating vs motivating)
3. Allow skipping levels? (Accessibility vs intended progression)
4. Save progress between sessions? (Nice to have but adds persistence layer)

## Decision: Keep It Simple
For initial implementation:
- No undo (can use reset)
- Show move count but not optimal
- Linear level progression
- No persistence (complete in one session)

These can be added later if the core game is solid.
