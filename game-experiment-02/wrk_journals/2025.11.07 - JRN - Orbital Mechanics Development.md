# Orbit Commander Development Journal

**Project**: Orbit Commander - Space Navigation Game with Orbital Mechanics
**Date Started**: 2025-11-07

## Project Overview

Creating a physics-based space navigation game for Round 3 of the game development competition. The game requires players to complete 10 increasingly difficult missions navigating a spacecraft through a realistic solar system using orbital mechanics, fuel management, and gravity assists.

## Key Requirements

1. Realistic orbital mechanics using Newtonian physics
2. 10 missions of increasing difficulty
3. Fuel-limited spacecraft with course correction capability
4. Real-time trajectory prediction visualization
5. Time acceleration controls
6. Score based on fuel efficiency and difficulty
7. Comprehensive test suite
8. Fully functional and bug-free

## Architecture Decisions

### 1. Physics Implementation

**Decision**: Implement custom Newtonian physics engine rather than using a library.

**Reasoning**:
- Fine control over accuracy vs. performance trade-offs
- Educational value - players experience real physics
- No external dependencies = smaller codebase
- Easier to debug and modify

**Formula Used**:
```
Force = G * (m1 * m2) / r²
Acceleration = Force / mass
Integration: Euler method, dt = 1/60 second
```

**Gravitational Constant**: G = 5.0 (adjusted for game balance and visible orbital effects)

### 2. Vector Math System

**Decision**: Implement pure functional vector operations.

**Benefits**:
- Immutable operations prevent bugs
- Easy to test in isolation
- Clear, readable code
- No class overhead

**Vector Operations**:
- `vectorAdd(a, b)` - Component-wise addition
- `vectorSubtract(a, b)` - Component-wise subtraction
- `vectorScale(v, s)` - Scalar multiplication
- `vectorMagnitude(v)` - Euclidean norm
- `vectorNormalize(v)` - Unit vector
- `vectorDistance(a, b)` - Euclidean distance

### 3. Trajectory Prediction

**Decision**: Use lookahead simulation without thrust for 100 steps.

**Why**:
- Shows player what will happen under gravity alone
- Helps with planning gravity assists
- Computationally affordable at 60 FPS
- Accurate enough for strategic planning

**Implementation**:
- Simulate 100 future physics steps
- Sample every 5th step for display
- Show 20 trajectory points
- Update every frame

### 4. Celestial Body System

**Design**:
- Sun at origin (0, 0) with mass 1000
- 6 main planets at various distances
- Moon orbits Earth as special case
- 1 asteroid with independent motion

**Orbital Speeds** (calculated for game balance):
- Mercury: 8 u/s at 300 units (fast, close)
- Venus: 6 u/s at 500 units
- Earth: 4.5 u/s at 700 units
- Moon: Special orbit, 30 units from Earth
- Mars: 3.5 u/s at 1000 units
- Jupiter: 2 u/s at 1600 units (slow, far)

### 5. Mission Progression

**Difficulty Scaling**:
1. Mars Bound: 1.0x - Introduction
2. Venus Run: 1.2x - Fuel efficiency focus
3. Lunar Deployment: 1.3x - Precision required
4. Gravity Assist: 1.5x - Introduces gravity assists
5. Mercury Challenge: 1.6x - Speed + precision
6. Fuel Conservation: 1.8x - Strategic fuel use
7. Asteroid Strike: 2.0x - Moving target
8. Dual Rendezvous: 2.2x - Multiple objectives
9. Grand Tour: 2.5x - Extended mission
10. Impossible: 3.0x - Ultimate challenge

**Fuel Limits**: 250-800 units, decreasing in later missions to force efficient play

### Phase 3: Trajectory Prediction (1 hour)

**Challenge**: Making trajectory prediction accurate AND fast.

**Solution**:
- Sample every 5th step (reduce points from 100 to 20)
- Only simulate 100 steps ahead (not entire mission)
- Don't include thrust in prediction (gravity-only)
- Cache results and update only when needed

**Result**: Smooth, accurate trajectory visualization without performance impact.

## Technical Challenges & Solutions

### Challenge 1: TypeScript Compilation

**Problem**: Complex type definitions and generic constraints.

**Solution**:
- Simplified type definitions
- Used `any` type for internal state passing
- Avoided complex generics
- Built incrementally, tested early

### Challenge 2: Physics Stability

**Problem**: Euler integration can be unstable, causing orbits to decay or diverge.

**Solution**:
- Kept timestep small (1/60 = 0.0167s)
- Used simple but reliable Euler method
- Validated energy conservation in tests
- Adjusted gravitational constant for game needs

### Challenge 3: Rendering Performance

**Problem**: 200 stars + 8 bodies + trajectory points at 60 FPS.

**Solution**:
- Culled off-screen objects
- Reduced trajectory points from 100 to 20 (via sampling)
- Simple drawing operations (circles, lines)
- No animations or effects

### Challenge 4: Trajectory Accuracy

**Problem**: Trajectory prediction must be accurate or players can't trust it.

**Solution**:
- Use exact same physics as main game loop
- Same timestep (1/60)
- Same gravitational constant
- No caching - recalculate each frame
- Validated against multiple orbits

## Design Insights

### 1. Orbital Mechanics Makes Good Game Mechanics

The physics naturally creates:
- **Learning curve**: Simple early missions, complex later ones
- **Challenge variability**: Different solutions for different approaches
- **Replayability**: Same mission can be completed multiple ways
- **Emergent complexity**: Gravity assists emerge naturally

### 2. Fuel as Primary Resource

Fuel management creates strategic depth:
- Limited thrust = limited corrections
- Encourages planning ahead
- Rewards understanding of gravity
- Naturally increases difficulty (less fuel in later missions)

### 3. Visualization is Critical

The trajectory prediction line is essential:
- Helps players understand physics
- Enables informed decision-making
- Educational value (shows gravity curves path)
- Makes physics visible and concrete

### 4. Time Scaling is Key Feature

Letting players speed up time:
- Reduces wait for long missions
- Lets them see consequences of maneuvers
- Makes game more accessible
- Enables "fast forwarding" past boring parts

## Lessons Learned

### 1. Physics First, Gameplay Second
Building solid physics early made everything else easier. The physics engine could be tested independently, and the game logic just had to make it pretty.

### 2. Immutable Operations Reduce Bugs
Using functional vector operations (no `this` or mutation) made the code more reliable and easier to test.

### 3. Visualization is Physics Education
Players intuitively understand gravity when they can see the curved trajectory. This is more effective than any explanation.

### 4. Constraints Create Creativity
Fuel limitations force players to think strategically. The constraints are features, not limitations.

### 5. TDD is Invaluable
Writing tests first (even if not strictly TDD) meant we caught physics bugs immediately rather than during gameplay.
