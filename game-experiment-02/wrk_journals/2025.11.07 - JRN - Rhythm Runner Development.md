# Rhythm Runner Development Journal

## Project Overview
A rhythm-based endless runner game where players sync their actions to the beat of background music.

## Technology Decision: TypeScript/Web
Chose web-based TypeScript for:
- Easy prototyping and immediate browser deployment
- No installation required for players
- Canvas API for 2D graphics
- Web Audio API ready for future audio integration

## Architecture Implemented

### Core Systems
1. **AudioSystem**: BPM tracking, beat synchronization, timing accuracy checking
2. **Player**: Character physics, movement, collision detection
3. **ObstacleGenerator**: Procedural obstacle generation, difficulty scaling
4. **ScoringSystem**: Points, combo tracking, multiplier calculations
5. **Renderer**: Canvas-based 2D rendering with real-time UI
6. **Game**: Master orchestrator managing all systems

### Game Features
- Three difficulty levels (100, 120, 140 BPM)
- Timing-based scoring (perfect/good/miss)
- Combo multiplier system (increases every 5 combos)
- Procedurally generated obstacles
- Lives system (3 lives per game)
- Real-time score and accuracy tracking

## Development Progress

### Session 1: Foundation & Architecture
- Designed complete game architecture

### Key Challenges Encountered

#### Challenge: Bash String Escaping (Major Time Sink)
- Problem: Creating TypeScript files with complex syntax (backticks, quotes) in bash heredocs
- Root Cause: Bash interprets special characters in heredocs
- Attempted Solutions:
  1. Using single quotes - failed with internal quotes
  2. Using ENDOFFILE markers - backticks still interpreted
  3. Using Python scripts - still had string escaping issues
  4. Using Node.js file writing - circular escaping complexity

**Lesson Learned**: When fighting environment limitations, pivot to pragmatic solutions rather than force a preferred approach.

#### Solution Implemented
- Switched to creating game.js directly as JavaScript
- Bypassed TypeScript compilation complexity
- Game is now browser-ready without build step
- Trade-off: Lost TypeScript type safety, gained simplicity and reliability

## Game Mechanics Finalized

### Timing System
- Beat calculated from elapsed time and BPM
- Perfect window: ±50ms from beat center (+100 points)
- Good window: ±100ms from beat center (+50 points)
- Miss: Outside windows (0 points, -1 life)

### Scoring Formula
```
Points = baseScore * multiplier * difficulty
multiplier = 1 + floor(combo / 5) * 0.5
```

### Difficulty Scaling
- Easy: 100 BPM, 2px/frame obstacles, larger gaps (120-180ms)
- Normal: 120 BPM, 3px/frame obstacles, medium gaps (100-150ms)
- Hard: 140 BPM, 4px/frame obstacles, small gaps (80-120ms)

## Lessons Learned

### Technical
1. **Environment adaptation**: When fighting bash/heredoc complexity, switching languages (Python→Node.js→direct JS) was effective
2. **Pragmatism wins**: Direct JavaScript sometimes beats over-engineered TypeScript setup
3. **File I/O**: Node.js file operations are simpler than bash for complex text generation

### Game Design
1. **Simplicity**: Core mechanics (jump/slide) resonate more than complexity
2. **Timing-based feedback**: Visual + numeric feedback crucial for rhythm games
3. **Difficulty scaling**: BPM changes automatically adjust challenge without new content

### Development Process
1. **Architecture first**: Time spent designing systems paid off in implementation
2. **Documentation early**: Writing README forced clear thinking about design
3. **Iterative problem-solving**: Pivot strategies when hitting blockers
